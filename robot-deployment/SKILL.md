# robot_deployment

处理机器人部署项目时，遵循以下约定。路径均以当前机器人项目根目录为起点，不是本技能所在的目录。

## 1. 语言

- 与用户沟通使用中文。
- 自己编写的日志说明、报告和供人复查的文档使用中文。
- Git commit 信息和代码注释使用英文。
- 命令、变量名、接口名、文件路径和工具输出保留原文。引用工具的原始日志时，用中文解释关键信息，不改写原始内容。

## 2. 表达

- 用直白、易懂的语言，优先使用常用词。
- 说明问题或分析结果时，先给结论，再按需要说明原因、依据和下一步；有多个要点时分条写清楚。
- 尽量不用专业术语。确实需要时，在第一次出现时用一句通俗的中文解释。
- 明确区分已确认的事实、推测和待验证的问题，不把猜测写成结论。

## 3. 文件存放与保留

- 需要长期保留、供人复查的项目管理文件统一放在项目根目录的 `review/` 下，例如重要决策、验收结果、部署记录和有后续价值的排查报告。项目已有明确的统一目录时沿用该目录，避免同时维护多套位置。
- 自己检查时生成、重要性较低但暂时还要使用的文件统一放在项目根目录的 `tmp/` 下，例如中间结果、临时截图和调试输出。
- 一次性复查结果或日志，如果用完后不会再用，直接在对话或终端中给出，不额外保存。工具必须生成文件时放入 `tmp/`，用完删除本次生成且确定不再需要的文件，不清理用户已有文件。
- 只在确实需要保存文件时创建相应目录；不为每次任务自动生成报告。
- `tmp/` 不纳入 Git 版本管理；需要时在项目现有的 `.gitignore` 中补充 `/tmp/`，保留原有内容。
- 上述规则针对管理文档和检查产物；源代码、测试、配置等仍放在项目原有的位置。

## 4. 模型任务不匹配与严重运行风险

- 部署或更换模型时，核对模型的训练或微调任务、适用条件与实际任务，尤其关注控制对象、输入输出含义和动作范围。不要因为模型能加载、程序能运行，就认定它适合当前机器人任务。
- 发现严重偏差，例如将针对某项任务微调的模型用于明显不适用的任务，必须在回复中显眼地给出 **⚠️ 警告：模型与当前任务严重不匹配**。发现可能导致碰撞、失控、人员受伤或设备损坏等严重运行风险时，显眼地给出 **⚠️ 警告：机器人运行存在严重风险**。相关运行日志也应使用独立的 `⚠️ 警告` 行，不能只藏在调试输出中。
- 警告用中文讲清楚：发现了什么、判断依据是什么、可能造成什么后果，以及现在应停止或修正什么。证据不足时明确标注“尚未确认”，不要将怀疑写成确定结论，也不要把普通的小问题都升级成严重警告。
- 严重风险尚未排除时，不继续启动或试跑可能引发危险的真实机器人动作。运行中发现严重风险时，优先使用已确认的安全停止方式；无法确认机器人已停止时，明确说明状态未知，并提示现场人员使用设备规定的停止或急停方式。

## 5. 运行程序必须可以主动终止

- 启动机器人运行程序前，必须明确一个实际可用的软件终止入口，例如前台程序的 `Ctrl+C`、停止命令或停止接口，并向用户说明具体操作方式。后台或远程运行时，也要有对应的停止入口，不能只依赖关闭终端。
- 编写或修改运行程序时，处理中断、停止请求和异常退出：停止继续下发动作，按设备或控制系统规定的方式让机器人进入安全停止状态，再完成必要清理。检查相关子进程和后台任务，避免主程序退出后仍继续发送控制指令。
- 不把“进程已经退出”等同于“机器人已经安全停止”。不得默认用强制杀进程、直接断电或将动作全部清零代替设备规定的安全停止流程。
- 在不引发真实危险动作的条件下验证终止机制，并说明已验证的范围。停止入口缺失、无效或尚未确认时，先补齐并验证，不启动会驱动真实机器人运动的程序；软件终止也不能替代设备规定的硬件急停措施。
