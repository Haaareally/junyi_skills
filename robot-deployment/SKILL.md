# robot_deployment

处理机器人部署项目时，遵循以下约定。先读取项目规则、当前状态入口和相关问题的已有主报告，再开展工作。只处理用户本次要求的范围；咨询、只读检查或规则整理不自动扩展为程序开发或实机运行。任务产物保存在用户指定的机器人项目中，不放在本技能所在目录；具体位置按第 3 节执行。

## 1. 语言

- 与用户沟通使用中文。
- 项目文档、报告和日志说明使用中文。
- 代码、代码注释和 Git commit 信息使用英文。
- 命令、变量名、接口名、文件路径和工具输出保留原文。引用工具的原始日志时，用中文解释关键信息，不改写原始内容。

## 2. 表达

- 用直白、易懂的语言，优先使用常用词。
- 开始向用户汇报时，先用一两句讲清楚已经做了什么，以及与当前任务相关的哪些工作还没做、哪些结果还没验证，再展开必要细节。任务刚开始时说明接下来要做什么，不把计划说成已经完成；没有未完成项时如实说明，不凑无关内容。
- 说明问题或分析结果时，先给结论，再按需要说明原因、依据和下一步；有多个要点时分条写清楚。
- 尽量不用专业术语。确实需要时，在第一次出现时用一句通俗的中文解释。
- 明确区分已确认的事实、推测和待验证的问题，不把猜测写成结论。

## 3. 当前状态、报告与证据

### 入口各司其职

- 沿用项目已有目录和入口。已有 `reports/` 就继续使用，不另建 `review/`；已有当前状态页就更新它，不再新建另一份 `STATUS.md` 或“最新进展”。没有约定且确需保存报告时，使用 `reports/README.md` 作为当前状态入口，不预先创建空目录和模板。
- 项目根 `README.md` 介绍用途、安装和常用入口。交付功能或部署入口时，按下节补齐终端示例；当前验证进度链接到状态页。
- 当前状态页回答：当前任务是什么、验证到了哪一步、还有哪些阻塞、下一步做什么。开头优先展示 3–5 个最相关的链接，历史实验放在后面的历史索引中，不与当前操作并列。标明更新时间和适用的模型、配置或版本；历史检查通过不代表当前机器人已就绪，状态页不能替代实际配置和启动前检查。
- `LOG.md` 记录历史变化，不充当当前操作说明。让读者从状态页就能了解现状，无需通读日志。
- 技能中只保留可跨项目复用的判断原则。具体机型、固件、现场现象及其处置依据记入相关问题主报告。
- 项目规则文件保存长期约定；实验进展、临时故障和当前可运行状态写入状态页及问题报告，避免多处维护同一结论。

### 在项目 README 中演示功能和部署

- 选一个最常用的任务，先用一句话说清“用户给什么、能得到什么”，再用终端展示一次调用和能辨认结果的关键输出。示例命令单独放在 `bash` 代码块，输出另放在 `text` 代码块，方便直接复制命令。
- 按操作者实际使用顺序写明工作目录、必要环境和配置、启动命令、就绪检查、功能调用与停止方式。服务需要持续运行时，分别标明哪个终端保持运行、在哪个终端发请求。若程序直接执行任务并退出，就展示实际任务入口和完成标志。
- 从当前版本的参数解析代码、配置和可用的 `--help` 核实参数。启动示例给出最小可用命令，再用一个常见用法展示如何改参数。写明关键参数的准确拼写、用途、必填或默认值、示例值，以及影响部署的单位或可选值。设备路径、模型路径等现场值要交代如何替换。
- 选取项目实际提供的就绪信号和功能输出。交付前在可用环境核对命令，注明示例是在本机、仿真还是真机验证的；只能从代码核对时，把输出标为预期并说明实测范围。会驱动实体运动的调用须在命令旁标明，并沿用第 4、5 节的警告与停止要求。

### 一个问题维护一份主报告

- 新增报告前，先查找已有的相关报告。同一问题、同一实验目标维护一份稳定的主报告，后续复测更新它；不按会话、日期或代理另建 `final`、`latest`、“复核版”等平行结论。只有独立的问题或实验目标需要单独报告，简短日志足以说明的变化不另建报告。
- 主报告按“当前结论 → 已验证范围 → 关键证据 → 未知项 → 下一步”组织。用中文解释图表的意义，不将测试数量、文件清单和校验值堆在开头；这些细节放在证据部分。
- 原始记录保留原始内容，不覆盖；供人阅读的结论随证据更新。旧结论保留在明确标记日期的历史部分，注明已被什么结果取代；当前操作说明撤下失效命令，不同时推荐新旧方案。涉及配置或程序版本的结论要注明对应版本，不把旧记录套用到新版本。
- 复测产生的原始数据沿用现有实验目录，从主报告链接。已有稳定证据直接引用，不为了目录整齐复制或搬动，不按原始文件数量增加阅读入口。
- 实验结论、阻塞或可执行条件发生变化时，同步更新问题主报告和当前状态页，并在 `LOG.md` 简述变化及链接。链接到已撤回的操作说明时，要同步更正引用。
- 子代理提交发现、证据路径和未确认项，由主代理统一更新当前状态、主报告结论和 `LOG.md`，不各写一份最终报告或重复追加日志。多个独立会话并行时，先核对最新文件及改动，保留其他会话内容；证据冲突要显式标出，不能无依据覆盖对方结论。

### 按复查价值保留文件

- 长期保留：实际驱动机器人执行的记录及异常记录，包括失败和中断；改变部署决策的实验；关键问题定位证据；正式验收结果。即使任务失败，也保留对应配置、版本、指令、反馈和退出原因等复查所需材料，不能因“未成功”归为临时文件。大体积原始数据可沿用项目现有的本地或外部存储约定，报告记录位置及必要的完整性信息，不强行全部纳入 Git。
- 临时保留：重复的只读探测、例行测试输出、中间图、未采用的分析及一次性排查脚本，放在项目根 `tmp/`。一旦其中的内容成为关键结论依据，先将必要证据保存到正式位置，再从报告引用；正式报告不依赖会清理的 `tmp/`。
- 无后续复查价值的输出直接在对话或终端中给出，不额外落盘。工具必须生成的临时文件放入 `tmp/`，仅清理本次生成且确定不再需要的文件；用户指定或工具要求时可使用系统 `/tmp/`。不擅自删除用户材料或历史实验。
- 正式功能、配置及需要重复运行的测试保留在已有业务、`tests/` 或 `evals/` 目录。不要把完整任务程序放进临时目录，也不要因为结果重要就保留全部一次性脚本和输出。
- `tmp/` 不纳入 Git；需要时在现有 `.gitignore` 中补充 `/tmp/`。只在确需保存时创建目录，不为每次对话自动生成报告或附件目录。

### LOG 只记录重要变化

- 使用用户指定机器人项目根目录的唯一 `LOG.md`。仅在结论、重要决策、阻塞状态或验证阶段变化时追加几行中文：变化是什么、验证到哪里、必要的下一步，以及主报告或证据链接；例行通过的检查、重复提醒和讨论过程不记流水账。
- 按实际发生时间追加，标明日期、时间及时区，保留历史内容。问题解决后追加结果，不删除旧记录。已有稳定材料用相对链接引用，不粘贴整份报告、终端输出或重复保存图片。

## 4. 安全边界、模型适配与严重运行风险

### 安全边界的来源

- 按当前机型、固件、控制模式和接口适用的官方动作范围与指令约束生成命令，保留设备保护和急停。具体动作按任务和现场配置选取。服务或脚本额外缩小角度、速度或时长，或通过步长、等待窗口、误差门槛、重复确认间接限制操作时，都须给出具体依据。“更稳妥”本身不足以设限。
- 官方边界尚未确认、实现无法可靠满足约束，或现场存在设备保护未覆盖的具体风险时，针对产生风险的操作设置相称的保护。临时保护写明解除条件和所需证据。依据变化时复核该措施能否继续控制原风险，再决定保留、调整或解除。严重风险仍未排除时，暂停受影响的实机操作。
- **凡影响正常使用的项目额外保护**，交付时须用直白中文标明其来源是项目，讲清限制了什么、防什么风险、怎样影响操作，以及临时限制何时可解除。运行中触发时，在相关界面或终端提示发生了什么、用户当前还能做什么。

### 模型适配与运行警告

- 部署或更换模型时，核对模型的训练或微调任务、适用条件与实际任务，尤其关注控制对象、输入输出含义和动作范围。不要因为模型能加载、程序能运行，就认定它适合当前机器人任务。
- 发现严重偏差，例如将针对某项任务微调的模型用于明显不适用的任务，必须在回复中显眼地给出 **⚠️ 警告：模型与当前任务严重不匹配**。发现可能导致碰撞、失控、人员受伤或设备损坏等严重运行风险时，显眼地给出 **⚠️ 警告：机器人运行存在严重风险**。相关运行日志也应使用独立的 `⚠️ 警告` 行，不能只藏在调试输出中。
- 警告用中文讲清楚：发现了什么、判断依据是什么、可能造成什么后果，以及现在应停止或修正什么。证据不足时明确标注“尚未确认”，不要将怀疑写成确定结论，也不要把普通的小问题都升级成严重警告。
- 当前警告须对应当前任务和具体操作，说明阻塞什么、需要什么证据才能解除。历史任务的不匹配或已解决风险留在相应历史报告，除非当前仍适用，不复制到新任务的状态页和启动说明。当前有效的警告应在相关启动入口清晰可见，不因减少重复记录而隐藏，也不逐条重复写入日志。
- 严重风险尚未排除时，不继续启动或试跑可能引发危险的真实机器人动作。运行中发现严重风险时，优先使用已确认的安全停止方式；无法确认机器人已停止时，明确说明状态未知，并提示现场人员使用设备规定的停止或急停方式。

## 5. 运行程序必须可以主动终止

- 启动机器人运行程序前，必须明确一个实际可用的软件终止入口，例如前台程序的 `Ctrl+C`、停止命令或停止接口，并向用户说明具体操作方式。后台或远程运行时，也要有对应的停止入口，不能只依赖关闭终端。
- 编写或修改运行程序时，处理中断、停止请求和异常退出：停止继续下发动作，按设备或控制系统规定的方式让机器人进入安全停止状态，再完成必要清理。检查相关子进程和后台任务，避免主程序退出后仍继续发送控制指令。
- 不把“进程已经退出”等同于“机器人已经安全停止”。不得默认用强制杀进程、直接断电或将动作全部清零代替设备规定的安全停止流程。
- 在不引发真实危险动作的条件下验证终止机制，并说明已验证的范围。停止入口缺失、无效或尚未确认时，先补齐并验证，不启动会驱动真实机器人运动的程序；软件终止也不能替代设备规定的硬件急停措施。

## 6. 条件满足后，交付能完整运行当前任务的实体程序

- 用户要求交付实体任务程序时，当安全终止方式已经确认可用，且控制代码、部署模型或程序及其模拟输出的动作指令均已检查、未发现严重问题时，交付必须覆盖当前任务的完整流程。不能只交付几秒钟、少量控制步或单次动作的短时测试来代替完整任务程序；仅要求分析、只读检查或规则整理时，不扩展为实机程序交付。
- 新增测试前，先明确待确认的问题和结果会改变的决定。已有日志、回放或同条件验证能回答该问题时，复用证据并继续任务。首次接管时验证相关接管行为，控制映射或停止机制改变时验证受影响的部分。确需用户到场时，说明验证目的，尽量在一次到场内分步完成必要验证。用户要求执行完整任务时，在满足运行条件并获得相应授权后执行。
- 程序按当前任务的完成条件正常结束；持续运行类任务运行到用户主动停止或触发必要的保护条件。不要无依据地设置很短的时限或步数而截断任务；保留有依据的安全时限、动作限制和异常停止机制，不为延长运行而关闭保护。
- 交付时说明启动命令、必要参数、任务完成判据、主动停止方式及已验证范围。模拟检查通过不等于实机任务已成功，未完成实机验证时如实说明；运行中出现第 4、5 节所述问题时，仍按相应警告和停止规则处理。
- 程序和说明交付完成不代表实机已经获准运行。实机执行仍须符合用户授权范围和当前检查条件，不把状态页或历史试验批准当作执行许可。
