# robot_deployment

处理机器人部署项目时，遵循以下约定。文件保存在当前任务的工作目录或机器人项目中，不放在本技能所在目录；具体位置按第 3 节执行。

## 1. 语言

- 与用户沟通使用中文。
- 自己编写的日志说明、报告和供人复查的文档使用中文。
- Git commit 信息和代码注释使用英文。
- 命令、变量名、接口名、文件路径和工具输出保留原文。引用工具的原始日志时，用中文解释关键信息，不改写原始内容。

## 2. 表达

- 用直白、易懂的语言，优先使用常用词。
- 开始向用户汇报时，先用一两句讲清楚已经做了什么，以及与当前任务相关的哪些工作还没做、哪些结果还没验证，再展开必要细节。任务刚开始时说明接下来要做什么，不把计划说成已经完成；没有未完成项时如实说明，不凑无关内容。
- 说明问题或分析结果时，先给结论，再按需要说明原因、依据和下一步；有多个要点时分条写清楚。
- 尽量不用专业术语。确实需要时，在第一次出现时用一句通俗的中文解释。
- 明确区分已确认的事实、推测和待验证的问题，不把猜测写成结论。

## 3. 日志、文件存放与保留

- 重要的、需要给人查看的日志统一写入当前任务工作目录的 `LOG.md`，包括部署进展、重要决策、验收结果和有后续复查价值的排查结论。用户指定了工作目录时使用该目录；未指定时以机器人项目根目录为准，不因临时切换子目录而新建多份日志。
- 按实际发生时间在 `LOG.md` 末尾追加记录，标明日期、时间和所用时区，保留已有内容，不覆盖或重写历史。每条用简短中文讲清楚本次进展和目前的问题，必要时补一句下一步；关键工作未做或尚未验证时直接说明。问题解决后追加结果，不删除原问题记录。
- 只记录有意义的变化，不重复粘贴旧进度，不把全部终端输出、讨论过程或例行检查流水写进日志。没有新进展或新问题时，不为凑记录而追加内容。
- 对理解关键进展或当前问题确有必要时，可在 `LOG.md` 中加入图片和数据：图片用 Markdown 嵌入，少量数据直接列出或用简短表格展示；需要单独保存的重要附件集中放在项目的 `review/assets/`，从日志用相对路径引用。已有稳定文件直接引用，不重复复制，也不引用即将清理的 `tmp/` 文件。
- 日志以 `LOG.md` 为统一入口，不再为同一进展建立其他日志文件。确有长期复查价值的重要设计说明、验证报告等材料统一放在项目根目录的 `review/`，并从日志链接；项目已有明确的复查材料目录时可沿用，重要日志仍统一写入 `LOG.md`。
- `review/` 及其附件只保留对重要部署决策、关键验证结论、问题定位或最终交付复查有实际作用的材料。普通检查输出、重复截图、零散调试记录和无关中间结果不加入；一条简短日志能说明白的，不额外生成报告。不因为文件已经生成就归档，也不擅自删除用户已有材料。
- 自己检查时生成、重要性较低但暂时还要使用的文件统一放在项目根目录的 `tmp/` 下，例如中间结果、临时截图和调试输出。
- 仅供当前检查、没有后续复查价值的一次性结果或调试输出，直接在对话或终端中给出，不额外保存；重要进展和问题仍按上述规则记入 `LOG.md`。工具必须生成临时文件时放入 `tmp/`，用完删除本次生成且确定不再需要的文件，不清理用户已有文件。
- 只在确实需要保存文件时创建相应目录；不为每次任务自动生成报告。
- `tmp/` 不纳入 Git 版本管理；需要时在项目现有的 `.gitignore` 中补充 `/tmp/`，保留原有内容。
- 上述规则针对管理文档和检查产物；源代码、测试、配置等仍放在项目原有的位置。

## 4. 模型任务不匹配与严重运行风险

- 部署或更换模型时，核对模型的训练或微调任务、适用条件与实际任务，尤其关注控制对象、输入输出含义和动作范围。不要因为模型能加载、程序能运行，就认定它适合当前机器人任务。
- 发现严重偏差，例如将针对某项任务微调的模型用于明显不适用的任务，必须在回复中显眼地给出 **⚠️ 警告：模型与当前任务严重不匹配**。发现可能导致碰撞、失控、人员受伤或设备损坏等严重运行风险时，显眼地给出 **⚠️ 警告：机器人运行存在严重风险**。相关运行日志也应使用独立的 `⚠️ 警告` 行，不能只藏在调试输出中。
- 警告用中文讲清楚：发现了什么、判断依据是什么、可能造成什么后果，以及现在应停止或修正什么。证据不足时明确标注“尚未确认”，不要将怀疑写成确定结论，也不要把普通的小问题都升级成严重警告。
- 严重风险尚未排除时，不继续启动或试跑可能引发危险的真实机器人动作。运行中发现严重风险时，优先使用已确认的安全停止方式；无法确认机器人已停止时，明确说明状态未知，并提示现场人员使用设备规定的停止或急停方式。

## 5. 运行程序必须可以主动终止

- 启动机器人运行程序前，必须明确一个实际可用的软件终止入口，例如前台程序的 `Ctrl+C`、停止命令或停止接口，并向用户说明具体操作方式。后台或远程运行时，也要有对应的停止入口，不能只依赖关闭终端。
- 编写或修改运行程序时，处理中断、停止请求和异常退出：停止继续下发动作，按设备或控制系统规定的方式让机器人进入安全停止状态，再完成必要清理。检查相关子进程和后台任务，避免主程序退出后仍继续发送控制指令。
- 不把“进程已经退出”等同于“机器人已经安全停止”。不得默认用强制杀进程、直接断电或将动作全部清零代替设备规定的安全停止流程。
- 在不引发真实危险动作的条件下验证终止机制，并说明已验证的范围。停止入口缺失、无效或尚未确认时，先补齐并验证，不启动会驱动真实机器人运动的程序；软件终止也不能替代设备规定的硬件急停措施。

## 6. 条件满足后，交付能完整运行当前任务的实体程序

- 当安全终止方式已经确认可用，且控制代码、部署模型或程序及其模拟输出的动作指令均已检查、未发现严重问题时，给用户在实体机器人上运行的代码或程序必须覆盖当前任务的完整流程。不能只交付几秒钟、少量控制步或单次动作的短时测试来代替完整任务程序。
- 短时测试可以作为前期验证步骤；条件满足后，继续完成正式运行入口、必要配置和任务执行流程，不停留在测试脚本。除非用户明确只要短时测试，否则默认交付完整任务版本。
- 程序按当前任务的完成条件正常结束；持续运行类任务运行到用户主动停止或触发必要的保护条件。不要无依据地设置很短的时限或步数而截断任务；保留有依据的安全时限、动作限制和异常停止机制，不为延长运行而关闭保护。
- 交付时说明启动命令、必要参数、任务完成判据、主动停止方式及已验证范围。模拟检查通过不等于实机任务已成功，未完成实机验证时如实说明；运行中出现第 4、5 节所述问题时，仍按相应警告和停止规则处理。
