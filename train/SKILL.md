# train

## 讲清模型怎样学习

- 用中文讨论方案、汇报进度，项目 README 和面向人的结论也用中文。代码、注释、程序生成的终端输出用英文，包括参数帮助、进度条、指标名、状态和报错。引用原始命令、标识符及第三方输出时保留原文。
- 先说任务的输入、希望模型给出的答案，以及用什么指标判断答案好坏。再沿一次训练样本的实际路径讲解：原始数据怎样变成输入，各模块接收什么、算出什么，预测怎样与目标比较，误差怎样更新需要学习的参数。指出哪些部分被冻结，哪些步骤只在训练时使用。
- 遇到关键特征（feature），用一个样本说清楚“这个值或向量代表谁、包含哪种信息、下一步拿它做什么”。只在有助于理解时标出形状和各维含义。做聚合、对齐、压缩或加入条件信息时，解释改动前后哪些信息被保留、混合或丢失，以及这对预测有什么影响。学习得到的特征只陈述结构或证据支持的含义，把推测标明。

## 用实验结果讨论方案

- 声称训练效果有提升时，说清用的是哪份数据、和哪次实验可比、具体指标变了多少。只有训练指标时，模型在新数据上的表现仍待验证。多项设置同时改变时，把观察到的变化和对原因的猜测分开。
- 对用户或自己提出的架构、调参判断，先用已有配置、曲线和评估结果核对，必要时查相关原始研究。若几种解释会导向不同方案，讲清各自依赖的条件和代价，给出当前倾向，以及哪项观察会让自己改选。

## 训练前和用户对齐数据准备

- 结合项目里的一个样本，用直白中文讲清楚原始数据怎样构造成训练样本、哪些内容作为输入、希望模型预测什么。给出输入和训练目标的形状（`shape`），按顺序解释每一维在当前任务中代表什么。
- 按项目实际情况说明数据怎样分组、哪些数据用于训练、其余部分用来做什么。和用户对齐样本含义及划分方式，沿用已经确认的约定，有影响训练的歧义时再具体询问。

## 启动 GPU 作业前确认用卡范围

- **实际启动前必须有用户为本次任务明确指定的 GPU ID。若未给出或编号含义不清，先问用户并等到答复，再创建训练会话或提交作业。** 这同样适用于占用 GPU 的短测、试跑、调参和续训。空闲状态、历史任务卡号、默认设备和现有环境变量都不能代替本次授权。设计、静态检查和 CPU 上的准备工作可以先做。
- 用户已指定本任务的卡时，沿用该范围。通过启动环境或调度器把主进程和全部子进程限制在指定卡上，核对宿主机 ID 与进程内编号的映射、分布式进程数及实际分配。遇到占用、显存不足或调度分配不符时，先在已授权范围内处理。需要换卡或增加卡时，先取得对应 ID。

## 让训练可查看、可中断、可恢复

- 用有明确名称的 `tmux` 会话启动正式训练，使终端断开后作业能继续运行。有作业调度器的环境可用其等效能力。每次运行使用唯一实验标识，将会话或作业号、配置和日志目录对应起来。启动后核对进程使用的设备、首批训练进度和日志落盘情况，再汇报是否正常启动。
- 用 `tqdm` 或框架等效的实时进度条展示轮次、已完成步数、总步数（已知时）、当前损失、学习率和处理速度。多进程训练由主进程显示一份。另将带步数的训练和验证指标持续写入可解析的日志，避免进度条刷新淹没文件。
- 保留中断前的日志和可恢复的检查点。按项目需要区分最新检查点与验证指标最佳的检查点。续训时核对模型、优化器、学习率计划和训练步数等必要状态，沿用可追溯的实验记录，避免覆盖旧结果。交付实际的查看、离开会话、主动停止与恢复命令。

## 充分使用已授权显存

- 在已授权卡上，用代表性的输入测量每卡峰值显存、实际吞吐量（每秒处理的样本或 token 数）和训练稳定性。逐步调整每卡单步处理的样本数及适合项目的数值精度，比较吞吐是否提高，并为最长输入、验证阶段和临时内存峰值留余量。
- 区分每卡单步批量与一次参数更新实际使用的总批量。调整卡数、每卡批量或梯度累积步数时，核对总批量、学习率和更新次数的变化。显存有余而速度不再提升时，检查数据读取、预处理或通信瓶颈。发生显存不足时根据日志调整受影响的配置，记录原因后重试。

## 让项目可以接手

- 在训练项目根目录维护中文 `README.md`，用简短目录图或列表解释模型、数据、配置、训练、验证及产物的位置。按真实入口给出可复制的环境准备、训练、查看进度、验证和续训命令，说明工作目录、关键参数、GPU ID 占位符及输出位置。用当前代码和参数帮助核对示例。
- 正式实验沿用项目现有的运行目录，无约定时用 `runs/<run-id>/`。保留原始日志、指标、实际使用的配置和检查点位置，记录代码版本、数据版本或划分、随机种子、设备及启动命令，使成功、失败和中断的运行都可追溯。大文件按项目约定存储。
- 给人看的关键进展和结论按时间追加到项目根 `LOG.md`。用几行中文写明改了什么、相对基线有什么结果、目前卡在哪里，并链接对应实验。日常排查过程和逐步训练输出留在各自实验记录中。
- 根目录沿用清晰、稳定的功能目录。一次性验证脚本、个人复盘草稿、调试输出统一放项目根的 `tmp/`，在项目 `.gitignore` 中保留或补充 `/tmp/`。明确指定系统 `/tmp/` 时使用该临时位置。正式训练日志、可复现结论的必要证据和长期复用的评测代码放在持久目录。
